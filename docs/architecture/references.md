# Nguồn best practice cho kiến trúc

Mọi quy tắc trong [overview.md](overview.md), [recipes.md](recipes.md), [module-structure.md](module-structure.md) và ADR-0017 phải trỏ về một mã nguồn ở bảng dưới (`[S-…]`). Quy tắc nào không có nguồn ngoài thì ghi rõ **[Dự án]**: đó là lựa chọn riêng của Life OS, kèm lý do. Như vậy agent và người đọc phân biệt được đâu là chuẩn chung, đâu là quyết định của mình.

Trích dẫn dưới đây là nguyên văn (tiếng Anh) do Claude đọc trực tiếp từ trang gốc ngày 01/11/2026. Dòng có ghi **chưa trích được** nghĩa là trang không đọc được bằng công cụ tự động. Quy tắc dựa vào nguồn đó phải kiểm lại bằng tay, nhiệm vụ ghi ở cột cuối.

## Kiến trúc và phụ thuộc

| Mã | Nguồn | Quy tắc lấy ra | Trích nguyên văn |
|---|---|---|---|
| S-HEX | Alistair Cockburn, [Hexagonal architecture (2005)](https://alistair.cockburn.us/hexagonal-architecture/) | App điều khiển được bởi người, chương trình, test. Mỗi thiết bị ngoài có một adapter. Thay DB bằng bản giả trong bộ nhớ để test | "Allow an application to equally be driven by users, programs, automated test or batch scripts". "an adapter to a "mock" database, one that sits in memory". "code pertaining to the *inside* part should not leak into the *outside* part." |
| S-CLEAN | Robert C. Martin, [The Clean Architecture (2012)](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) | Phụ thuộc chỉ hướng vào trong. Vượt ranh giới bằng đảo phụ thuộc (lớp trong định nghĩa interface, lớp ngoài cài đặt). Dữ liệu qua ranh giới là cấu trúc đơn giản, không phải dòng DB. Luật nghiệp vụ test được không cần UI hay DB | "source code dependencies can only point *inwards*". "using the Dependency Inversion Principle". "We don't want to cheat and pass *Entities* or Database rows." "The business rules can be tested without the UI, Database…" |
| S-ROOT | Mark Seemann, [Composition Root (2011)](https://blog.ploeh.dk/2011/07/28/CompositionRoot/) | Một chỗ duy nhất ghép module, sát điểm vào app. Thư viện không có gốc ghép | "A Composition Root is a (preferably) unique location in an application where modules are composed together." "As close as possible to the application's entry point." "Only applications should have Composition Roots. Libraries and frameworks shouldn't." |
| S-TMA | Tuist, [The Modular Architecture (TMA)](https://tuist.dev/en/docs/guides/features/projects/tma-architecture) (tên cũ µFeatures) | Mỗi module gồm Feature, Interface, Testing, Tests, Example. Module phụ thuộc **interface** của module khác, không phụ thuộc cài đặt. App ghép cài đặt lúc chạy. Bản giả và dữ liệu mẫu ở target Testing, dùng được cho preview | "When a module depends on another module, it declares a dependency against its interface target." "Depending on interfaces requires apps to build the graph of implementations at runtime, and dependency-inject it". "Developers should be able to **build, test, and try** their features fast". |
| S-ISO | Point-Free, [isowords README, Hyper-modularization](https://github.com/pointfreeco/isowords) | App thật chia 86+ module SPM để build nhanh, preview ổn định, có app preview chỉ build một phần | "This allows us to work on features without building the entire application, which improves compile times and SwiftUI preview stability." |
| S-APPLE-PKG | Apple, [Organizing your code with local packages](https://developer.apple.com/documentation/xcode/organizing-your-code-with-local-packages) | Chia code bằng Swift package cục bộ để dễ bảo trì | "organize its code in a modular way to keep it maintainable by creating Swift packages and using them as local packages." |
| S-DEPS | Point-Free, [swift-dependencies README](https://github.com/pointfreeco/swift-dependencies) | Tự kiểm soát phụ thuộc, có bản live, preview, test riêng | "it is highly encouraged for you to take control of your dependencies rather than letting them control you." "override dependencies just for previews without affecting how your app will run in production." |

## SwiftUI và trạng thái

| Mã | Nguồn | Quy tắc lấy ra | Trích nguyên văn |
|---|---|---|---|
| S-OBS | Apple, [Managing model data in your app](https://developer.apple.com/documentation/swiftui/managing-model-data-in-your-app) | Dùng macro `@Observable`. View sở hữu model thì khai báo `@State private`. Cần binding thì `@Bindable`. Chia sẻ sâu thì `@Environment`. View chỉ theo dõi thuộc tính nó đọc trong `body` | "always use the `Observable` macro when adding observation support to your type." "declare a private variable … Then add the State() macro". "If `body` doesn't read any properties of an observable data model object, the view doesn't track any dependencies." |
| S-MODEL | Apple, [Model data](https://developer.apple.com/documentation/swiftui/model-data) | Trạng thái UI tạm thời dùng `@State` trong View. Mỗi dữ liệu có một nguồn sự thật | "Manage transient UI state locally within a view by wrapping value types as State() properties." "maintain a single source of truth for every piece of data in your app." |
| S-PERF23 | Apple WWDC23, [Demystify SwiftUI performance](https://developer.apple.com/videos/play/wwdc2023/10160/) | `body` phải rẻ. View chỉ nhận dữ liệu nó cần. Không lọc dữ liệu hay nội suy chuỗi đắt trong `body`. List cần ID ổn định, số view mỗi hàng không đổi, tránh `AnyView` | "It's important that body itself is as cheap as possible." "Try reducing view values to only the data they actually depend on." "avoid using AnyView and lopsided conditions." |
| S-PERF25 | Apple WWDC25, [Optimize SwiftUI performance with Instruments](https://developer.apple.com/videos/play/wwdc2025/306/) | Thân view chạy lâu là nguyên nhân phổ biến. Tạo formatter một lần, dùng lại. Mỗi hàng chỉ phụ thuộc model của chính nó, không phụ thuộc cả mảng | "View bodies that take too long to run are a common cause of performance problems in SwiftUI". "I can reuse the formatters". "each view only depends directly on its own landmark's view model." |
| S-LAZY | Apple, [Creating performant scrollable stacks](https://developer.apple.com/documentation/swiftui/creating-performant-scrollable-stacks) | Bắt đầu bằng stack thường; chỉ đổi sang Lazy khi đo thấy lợi. Đo trên máy thật | "always start with a standard stack view and only switch to a lazy stack if profiling your code shows a worthwhile performance improvement." "Never profile your code using the iOS simulator." |
| S-PREV | Apple, [Previews in Xcode](https://developer.apple.com/documentation/swiftui/previews-in-xcode) | Dùng macro Preview; `PreviewModifier` dựng môi trường cho preview | "You use one of the preview macros — like Preview(_:body:) — to tell Xcode what to display." |

## Dữ liệu

| Mã | Nguồn | Quy tắc lấy ra | Trích nguyên văn |
|---|---|---|---|
| S-GRDB-REC | GRDB, [Recommended Practices for Designing Record Types](https://github.com/groue/GRDB.swift/blob/master/GRDB/Documentation.docc/RecordRecommendedPractices.md) | Một record type cho một bảng, là struct khớp cột. Thiết kế schema chắc trước. Cột NOT NULL thì thuộc tính không optional. Request đặt trong extension, cột trong enum `Columns` lồng trong record | "Define one record type per database table." "define a **robust database schema** even before playing with record types." "a dedicated enumeration, with the name `Columns`, nested inside the record type." |
| S-GRDB-CONC | GRDB, [Concurrency](https://github.com/groue/GRDB.swift/blob/master/GRDB/Documentation.docc/Concurrency.md) | Mở đúng một `DatabasePool` cho mỗi file DB suốt vòng đời app. Tự khoanh transaction. Dữ liệu đọc ra coi như đã cũ; muốn mới thì dùng `ValueObservation` | "Open one single `DatabaseQueue` or `DatabasePool` per database file, for the whole duration of your use of the database." "immediately consider it as *stale*." |
| S-GRDB-MIG | GRDB, [Migrations](https://github.com/groue/GRDB.swift/blob/master/GRDB/Documentation.docc/Migrations.md) | Không bao giờ sửa migration đã phát hành. Schema viết bằng chuỗi SQL, không dựa vào type của app. `eraseDatabaseOnSchemaChange` chỉ trong `#if DEBUG` | "A good migration is a migration that is never modified once it has shipped." "migrations should not depend on application types." "hide it behind `#if DEBUG`". |
| S-SQLD | Point-Free, [SQLiteData README](https://github.com/pointfreeco/sqlite-data) | `@Table`/`@FetchAll` thay `@Model`/`@Query`. Cấu hình DB và `SyncEngine` ở điểm vào app, càng sớm càng tốt | "simply configure a `SyncEngine` in the entry point of the app". "This is typically done as early as possible in your app's lifetime". |
| S-SQLD-CK | Point-Free, bài CloudKit trong tài liệu SQLiteData | Luật schema khi đồng bộ (khoá UUID, không UNIQUE, hành động khoá ngoại, migration chỉ thêm) | **Chưa trích được**: trang tài liệu không đọc được bằng công cụ. Luật hiện có trong `schema/0001_initial.sql` lấy từ trang cộng đồng. **LOS-021 phải đối chiếu bài gốc** trước khi chốt schema. |

## Swift: tên, file, test, concurrency

| Mã | Nguồn | Quy tắc lấy ra | Trích nguyên văn |
|---|---|---|---|
| S-API | Swift.org, [API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/) | Rõ ràng tại chỗ dùng. Protocol mô tả "là gì" thì đặt danh từ; mô tả khả năng thì `-able/-ible/-ing`. Comment tài liệu mở đầu bằng một câu tóm tắt | "**Clarity at the point of use** is your most important goal." "Protocols that describe *what something is* should read as nouns". "Begin with a summary that describes the entity being declared." |
| S-GOOG | Google, [Swift Style Guide](https://google.github.io/swift/) | File chứa một type thì mang tên type. Extension thêm conformance: `Type+Protocol.swift`; nhiều extension: `Type+Additions.swift`. Thường một type cấp cao mỗi file. Tổ chức file theo một logic giải thích được | "A file that primarily contains a single type has the name of that type." "`MyType+MyProtocol.swift`". "most source files contain only one top-level type". |
| S-AIRBNB | Airbnb, [Swift Style Guide](https://swift.airbnb.tech/) | Bool đặt `is/has`. Tránh hàm toàn cục, dùng `enum` không case làm namespace hằng. Access control chặt nhất có thể | "Name booleans like `isSpaceship`, `hasSpacesuit`, etc." (hai quy tắc sau lấy từ phần trang đọc qua tóm tắt, cần kiểm lại nguyên văn) |
| S-TEST | swiftlang, [Swift Testing](https://github.com/swiftlang/swift-testing) | `@Test` và `#expect`. Test tham số hoá thay vì lặp code. Test chạy song song mặc định nên không chia sẻ trạng thái | "Parameterized tests let you write less code by running the same test over many different inputs." "run in parallel by default." |
| S-CONC | Swift.org, The Swift Programming Language, chương [Concurrency](https://docs.swift.org/swift-book/documentation/the-swift-programming-language/concurrency/) | Actor cách ly trạng thái dùng chung; ưu tiên task có cấu trúc | **Chưa trích được** (trang render bằng JavaScript). Quy tắc concurrency trong conventions §4 đang dựa vào ngữ nghĩa Swift 6 và chế độ strict concurrency của trình biên dịch. LOS-004 đối chiếu lại. |

## Quy tắc riêng của dự án [Dự án]

Những điều sau không có chuẩn chung để trích. Chúng là lựa chọn của Life OS, đã ghi trong ADR:
- Không có lớp UseCase; luật nghiệp vụ là hàm thuần trong `Domain/Rules` (ADR-0017). S-CLEAN có lớp Use Cases, nhưng app một người dùng không cần lớp riêng.
- Port và read model nằm chung trong `Domain` thay vì mỗi tính năng một target Interface như S-TMA. Lý do: mọi tính năng đọc cùng một DB, và 9 target Interface sẽ gấp đôi số target mà không tách được gì thêm. Tín hiệu xem lại: có tính năng cần ẩn kiểu của nó khỏi tính năng khác.
- Bản giả gom ở `TestSupport` (đóng vai target Testing của S-TMA cho cả lõi).
- Danh sách thư mục cố định trong mỗi target và script `check_structure.py`. S-GOOG chỉ đòi "một logic giải thích được"; dự án chọn logic cụ thể để agent không phải đoán.
